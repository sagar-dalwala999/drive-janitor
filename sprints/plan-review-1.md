### Q2: Is every sub-Generator slice independent?
- **Verdict:** PUSH BACK
- **Class:** STRUCTURAL — affects **S6, S7** (contract gap #1) and **S5, S6** (contract gap #2)
- **File-ownership walk (mechanical check first):** S1–S7's file lists are pairwise disjoint (`Scanner.BuildCache.psm1`, `Scanner.BrowserApp.psm1`, `Scanner.Projects.psm1`, `Scanner.System.psm1`, `Cleaner.psm1`, `ui/MainWindow.xaml`+`ui/Gui.ps1`, `DriveJanitor.ps1`+`Config.psm1`+`Install-Shortcut.ps1`+`README.md`). No two slices write the same file. That part of the collision defense is sound. Two contract gaps remain underneath it, though:

  **Gap 1 — S6↔S7 scan orchestration has no declared contract.** The spec's "frozen Core contract" section fully pins `New-Finding`, `Test-PathProtected`, `Clear-PathContents`, `Get-DirSize`, `Format-Size`, `Write-JanitorLog`, and S5 separately gets a fully-specified `Invoke-Clean -Findings -DryRun -ProgressCallback` signature. **Nothing equivalent exists for the scan.** S7's scope says it "wires the scan orchestration (run all four scanners, aggregate findings)"; S6's scope says it must run the scan in "a runspace/BeginInvoke" and marshal progress via `Dispatcher.Invoke`. These are the same responsibility (own an async scan + report per-root progress) assigned to two different files with no shared function name, parameter shape, or aggregated-findings shape written down anywhere. Built independently, the two realistic outcomes are: (a) S6 hardcodes calls to all four `Invoke-*Scan` functions itself, making S7's "wires the orchestration" claim dead code, or (b) S6 calls a function S7 never actually implemented under that name. Either way it's a rebuild at integration, exactly the "hours of wrong work" this framework exists to prevent.
  **Fix required before dispatch:** add an explicit line to spec.md, e.g. `Invoke-AllScans -Roots <string[]> -ProgressCallback <scriptblock> -> [pscustomobject[]]`, name which file owns it (S7, since DriveJanitor.ps1 already claims the orchestration role), and state that S6 calls it — mirroring how S5's contract is already written. Also state explicitly that Clean, not just Scan, must run off the UI thread (S6's text only says "must not freeze" for Scan; DISM analysis and large robocopy mirrors during Clean are equally capable of freezing the window, and `-ProgressCallback` already exists on `Invoke-Clean` to support this — it just needs the same one-sentence requirement S6 already has for Scan). This second half is a clarification of existing intent, not a new contract — fold it into the same spec edit but it does not by itself need to gate dispatch.

  **Gap 2 — S5's `Actual` field is ambiguous, and S6 binds to it.** S5's contract says: "Measure real reclaim as a `Get-PSDrive` free-space delta per drive... return both predicted and actual." That means `Actual` = whole-drive delta. See Q-verification below for why that's the wrong number to gate on — but regardless of which number is "right," **S6's result panel needs to bind to a specific field name and know what it means**, and right now the contract text and the acceptance criterion don't agree with what's implementable. This is a second, smaller instance of the same problem as Gap 1: a cross-slice data shape assumed rather than pinned.
  **Fix required before dispatch:** change S5's return contract to expose both a deterministic per-path sum (already computed internally by `Clear-PathContents`'s before/after `Get-DirSize` around each robocopy call — just needs to be accumulated and returned) and the whole-drive delta, under two distinctly-named fields, e.g. `ActualPathBytes` (deterministic, this is what the 5% acceptance check should key off) and `ActualDriveDeltaBytes` (informational only, reported to the user for transparency, not gated). State in spec.md which one the GUI's "predicted vs actual" panel should treat as ground truth.

### Q3: Does the frozen foundation (Core.psm1, in place of Track B) actually hold — and is it safe enough for 7 slices to build against?
- **Verdict:** PUSH BACK
- **Class:** STRUCTURAL — the fix lives in `modules/Core.psm1` / `tests/Guard.Tests.ps1`, which **no slice may touch**. This must be patched by Main Claude directly, not delegated to any of S1–S7. Directly affects **S5** (the only slice that calls `Clear-PathContents`), and by extension every path any scanner (S1–S4) ever hands to it.
- Ownership-wise the "do not touch" rule is correctly drawn — Core.psm1 and Guard.Tests.ps1 are correctly kept out of every slice's scope, which is exactly what this question checks for. The problem is not who owns the foundation file. **The problem is that the foundation file, as written, has two real bypasses of the safety guard that every future slice is trusting to be sound.** This is the highest-value finding in this review — the guard is the only thing standing between a scanner bug and permanent data loss on a real machine with real work on it.

  **Finding A — `Test-PathProtected` matches the literal string, not the resolved path. Trailing spaces/dots defeat it.**
  Trace `Test-PathProtected("C:\Windows\System32 ")` (one trailing space) through the actual code:
  - `TrimEnd('\')` only strips backslashes — the trailing space survives.
  - Exact-match loop: `"C:\Windows\System32 " -ieq "C:\Windows\System32"` → **false** (different strings). No match.
  - Pattern loop: none of the 5 regexes reference System32. No match.
  - Segment count = 3 (`C:`, `Windows`, `System32 `) → not caught by the "shallower than 3 segments" rule.
  - Leaf = `"system32 "` (space preserved after `.ToLower()`) → not in `$SourceLeaves`. Ancestor = `Windows` → not in `$SourceAncestors`. Not the tool's own dir.
  - **Returns `$false` — unprotected.**

  Windows' own Win32 path canonicalization (used by `CreateFile`/`Test-Path`/`robocopy` when a path is *not* `\\?\`-prefixed) strips trailing spaces and dots from path components before resolving them to a filesystem entry — this is standard, well-documented Windows path behavior, not something I ran on this machine to confirm empirically. The practical consequence: `"C:\Windows\System32 "` (or any `ProtectedExact` entry with a trailing space or dot appended) very likely **resolves on disk to the real protected directory** even though the guard's literal-string check says it's fine. Feed that string into `Clear-PathContents` and `robocopy $empty $Path /MIR` mirrors an empty directory into the real System32. The same technique defeats the `.git`/`modules-2`/pagefile regex patterns too — `\\\.git($|\\)` requires `.git` at end-of-string or immediately before a backslash, so `...\.git ` (trailing space) doesn't match the pattern either, for the same underlying reason. A separate but related gap: the guard operates on the literal split of the string, so a path containing literal `..` segments (e.g., a hand-typed custom root, or a relative reparse-point target read back verbatim) is never resolved to its canonical absolute form before matching — `D:\projects\foo\..\..\..\Windows\System32` passes every check in the function and returns `$false`.
  None of these three shapes (trailing space, trailing dot, embedded `..`) has a test case in `Guard.Tests.ps1` today.
  **Required fix:** canonicalize before matching (resolve `..`/`.` to an absolute form) and explicitly reject any path where a segment ends in a trailing space or dot — no legitimate `Get-ChildItem`-enumerated path will ever have one, so this is a safe, low-cost rejection rule, not a source of false blocks. Add test cases for all three shapes to `Guard.Tests.ps1`.

  **Finding B — `Clear-PathContents`'s `robocopy ... /MIR` has no `/XJ`. This is the one I'd expect to fire for real, with no adversary at all.**
  You asked me to think hard about what `/MIR` does when the target is a junction into a directory the user cares about — I did, and the code has no defense against this at all. `robocopy /MIR` without `/XJ` (exclude junctions) is a well-known, widely-documented source of exactly this kind of disaster: by default robocopy descends into directory junctions/reparse points it encounters and mirrors through them rather than treating them as opaque links, which for a `/MIR` (mirror-from-empty) operation means **deleting the real contents at the junction's target location**, which can be anywhere on the filesystem — a different drive, a different project, a network share. This is not a hypothetical crafted-input attack; it's an everyday occurrence on exactly the ecosystem this tool targets: pnpm's content-addressable store uses linked/symlinked structures, Android SDK installs commonly use junctions for shared component caches, OneDrive/Docker Desktop/WSL integrations create reparse points routinely, and this machine specifically has a stated near-duplicate-project situation (`D:\A` vs `D:\Pulse`, called out in S3) that raises the odds of some linked/shared directory structure existing somewhere under the scanned roots. There is currently zero code path that detects a reparse point inside a target directory before robocopy is invoked, and zero test coverage for it.
  Separately: `Get-DirSize` (`Get-ChildItem -Recurse -Force -File`) is also not guarded against reparse points — Windows PowerShell 5.1's `Get-ChildItem -Recurse` is documented to follow directory junctions/symlinks by default, which risks both wildly wrong size reporting (counting a linked-to directory's contents as if they belonged to the scanned path) and, in the pathological case of a circular junction, a hang.
  **Required fix:** add `/XJ` to the `robocopy /MIR` invocation in `Clear-PathContents` (or an equivalent explicit reparse-point exclusion), and add a pre-flight check that treats any reparse point found inside a would-be-cleaned path as `Report`-only/`Advanced` rather than something scanners silently recurse into and the cleaner silently mirrors through. Add a test case (can be a `-WhatIf`-based logic test if a real junction fixture is impractical in CI) confirming a reparse point is not traversed.

  Both A and B live in the frozen contract every one of the 7 slices trusts. **S1–S4, S6, S7 can still be dispatched now** — none of their signatures change, only `Test-PathProtected`'s internal logic and `Clear-PathContents`'s robocopy flags do. But **S5's output must not be treated as safe to run against the real machine, and no real Clean should ever be executed, until this lands and the guard suite is re-verified green** (existing 22 + new cases for trailing-space, trailing-dot, `..`, and reparse-point behavior).

**REVISE**

Four STRUCTURAL items, all cheap to fix (spec-text additions + a Core.psm1 patch that doesn't touch any function signature), none of which require re-slicing the DAG. S1–S4, S6, S7 do not need to wait on these fixes to be *dispatched* — but S5 must not be treated as done, and no real Clean must run on the real machine, until the Core.psm1 guard hardening lands and Guard.Tests.ps1 is re-verified green.

## If REVISE: priority order of fixes

1. **[STRUCTURAL — Core.psm1, blocks trusting S5's output]** Canonicalize `Test-PathProtected`'s input (resolve `..`, reject trailing space/dot segments) before running exact/pattern/segment checks. Add test cases for trailing-space, trailing-dot, and `..`-traversal variants of existing protected entries.
2. **[STRUCTURAL — Core.psm1, blocks trusting S5's output]** Add `/XJ` (or equivalent) to the `robocopy /MIR` call in `Clear-PathContents`, and add a pre-flight reparse-point check so scanners/cleaner never silently recurse through a junction/symlink. Add a guard test.
3. **[STRUCTURAL — S6, S7]** Add an explicit scan-orchestration contract to spec.md (`Invoke-AllScans -Roots -ProgressCallback -> findings[]`, owner = S7, caller = S6), and add the one-line requirement that Clean, not just Scan, runs off the UI thread.
4. **[STRUCTURAL — S5, S6]** Split S5's `Actual` field into a deterministic `ActualPathBytes` (sum of per-path before/after size, gates the 5% acceptance check) and an informational `ActualDriveDeltaBytes` (whole-drive `Get-PSDrive` delta, reported but not gated) — see Q-verification detail under Q2. Whole-drive free-space delta is not a reliable pass/fail signal on a machine with concurrent disk activity (browsers, sync clients, IDEs, Windows Update) during a multi-minute clean; per-path measurement is.
5. [NON-STRUCTURAL] Defer item 8 (duplicate/stale project finder) and item 9 (Advanced flow: custom roots/thresholds/exclusions/saved config) to Phase 5 — neither is covered by any MVP Acceptance Criterion, and item 9's custom-root input is the one path into the guard's blind spot for drives other than C:/D: (the hardcoded `ProtectedExact` list only covers C:\ and D:\-rooted paths by name; other drives only get the generic "shallower than 3 segments" fallback).
6. [NON-STRUCTURAL] Carry `build_class`, `qa_depth`, `capabilities:` into spec.md's header verbatim; separately confirm `greenfield-crud` is the right taxonomy bucket for a destructive scan/clean utility.
7. [NON-STRUCTURAL] `surface: desktop-ui` → consider `mixed` (GUI + `-CLI` both exist), or confirm Phase 3 recognizes the custom value.
8. [NON-STRUCTURAL] No slice currently owns an icon asset, but S7's `Install-Shortcut.ps1` needs "a sensible icon" — assign an owner (or specify using a stock Windows shell icon by index, which needs no new file).
9. [NON-STRUCTURAL] S4's big-file finder (>500MB, outside protected paths) can re-report files already counted inside S1/S3's categorized findings (e.g., a huge file inside `android\build` or `node_modules`), double-counting GB in the GUI's running total. De-dupe by path prefix before totaling.
10. [NON-STRUCTURAL] Minor naming nit: S3's file is `Scanner.Projects.psm1` but its function is `Invoke-ProjectScan` (singular) — harmless since the name is fully pinned in spec text, but worth aligning.
